# Internal operational records

Project registration and operating history belong to the installation's private
storage. This applies to public and private projects. Connecting GitHub manages
project repositories; it must not require users to publish registration records
or configure another records repository.

The contract is [instance-operational-records.yaml](../contracts/instance-operational-records.yaml).
This is approved architecture under unpublished maintenance, not an operating
capability claim. Do not change the live authority or submit new private project
data through the existing source-backed registration route before qualification.

## Existing installation and migration

Shared policy, software, schemas and source review remain versioned. Current
Git-backed installation records retain their authority and evidence until an
explicit migration binds the exact source revision, record digest and original
envelope. Pending Git reviews resume their original request and authority.
The internal store must not silently shadow a source record with the same key or
provider identity. A private copy of a public source snapshot is still a cache.

New operational repository registrations use one internal record identity for
intake, setup and inventory. Promotion changes that identity's state atomically.
Every accepted change has a version, digest, authenticated decision, readiness
evidence and immutable receipt. Replay returns its original result; stale or
conflicting changes fail before mutation. A compensating change preserves history.

## Operator path

The Console continues to derive provider identity from the repository connection.
The operator reviews and accepts a registration decision. OOS validates and
coordinates it; WGCF evaluates policy and persists the accepted result in its
existing private database. The result is read back from that authority. It must
not present a fabricated pull request or merge requirement for an internal record.
Source code changes still follow the existing Gary author and human review path.

Repository setup, source authority, selectors and history must consume that same
internal record before the route can be called operational. A storage-only test
does not qualify the full workflow. Legacy records remain readable alongside the
new route with explicit authority provenance; unavailable authority must not be
shown as an empty successful register.

Platform's independent source reader may resolve eligibility by canonical owner
key or by the exact immutable GitHub repository ID. Provider lookup returns one
installation-bound proof; it is not a register export and must not assume that
the canonical key equals the GitHub repository name. Its distinct optional
read-only role admits only these eligibility routes. Registration, generic
metadata/history reads and reconciliation remain outside that role.

Delivery's existing repository-readiness check consumes this same current active
source-only admission. Its receipt binds the actual installation, record version,
digest and accepted source-authority policy. It does not require a fabricated
public repository-rule file or another application test to accept registration.
Before linking, the check reevaluates current eligibility; suspension, stale
evidence or an unavailable internal authority blocks the operation. This consumer
extension does not migrate Delivery Catalog records or enable private Studio.

## Privacy and recovery

Keep project names, URLs, descriptions, plans, private source and decision history
out of public source records, generated public routing files and public Studio.
Installation-local projections may expose them to the authorized operator. Do
not automatically send contents to a model during registration. Approved model
use remains possible under provider policy and context admission.

Back up internal records, immutable revisions and receipts together. On recovery,
verify their bindings before serving them as authority. A corrupt record is an
unavailable authority, not a reason to reconstruct it from a public Git copy or
discard the original operation. A missing store must not create a fresh empty
installation over retained data.

For packaging, installation records are internal state. This maintenance does
not build an installer or migrate unrelated workflows. Current source-backed
Intake and Inventory instructions remain the legacy procedure until the new
route is qualified and explicitly activated.

## Integration and publication order

Keep this as coordinated maintenance in the current unpublished batch. It must
not turn into separate ART children or a new records service.

1. Governance defines the internal authority and record/receipt shapes. Existing
   source-backed instructions apply only to their retained legacy requests.
2. WGCF supplies transactional persistence and bounded authenticated reads. The
   transition adapter must reevaluate the actual current record and validate
   the accepted decision/readiness; the storage callback alone is not that adapter.
3. OOS retains the selected authority with each request. New internal decisions
   finish from durable internal readback. Legacy source requests resume their
   original review/merge path. Do not translate an internal acceptance into a
   pretend Git review or replace an uncertain request with another identity.
4. The Console keeps the existing registration forms and derives known provider
   fields. It shows the actual approval/result and authority, including loading,
   conflicts and recovery. Inventory selectors and continuity must include the
   same internal records with distinct provenance and without shadowing legacy keys.
5. Platform's bootstrap, source issuer and ordinary source readers consume the
   same internal owner decision. Installation-local rule/context projections
   stay private; no private routing entry is generated into a public repository.
   Separately qualify the approved exact-repository read-only source inspection.
6. Security reviews the complete source delta. After batch publication is
   authorized, land policy before dependent runtime source, refresh actual
   contract pins, accept the exact composition and qualify native operation.

The first proof covers standalone private repository custody, registration,
source setup, admission and manually authored reviewed source, including retry
after interruption. Existing public records stay readable. Shared policy and
code review are retained. Later migration of Proposal, Studio, Catalog and other
operational records follows the same internal-storage target; this repository
route does not claim those currently source-backed workflows are already private.
In particular, a private source connection must not copy a client project into
the current public Studio as a shortcut.


## Native source-only Inventory semantics

The internal Inventory request uses the same admitted source-only scope and
metadata rules as the retained source workflow. Promotion preserves the physical
provider, admitted class and Security-binding classification. It changes the
existing aggregate phase and increments its current version, rather than resetting
a second record to version one. Its lineage retains the actual Intake version and
digest. This grants neither current app acceptance nor runtime activation.

Updates preserve physical identity and current posture. Suspension and retirement
deny new source references; restoration records another explicit decision bound
to the latest suspension or retirement receipt. The existing reason, impact and
approval requirements remain for lifecycle actions. Promotion adds no new CI,
application-testing or separate verification gate. Readiness is evaluated from the
real accepted record under current Governance policy.

Native source eligibility uses the same pure source-owner rules as the source
workflow. Proposed and admitted Intake can prepare source-only setup; only active
Inventory can satisfy ordinary source eligibility. Read-only projection itself
issues no credential or source permission. It binds installation, current record
version/digest and policy, with a second read to detect changes.

Registry metadata reads are paged, searched and counted by the database. They
never require loading every project's history. Each returned page names its
selection and continuation, and each native record retains its own namespace and
version. Legacy Git projections remain separately attributable. An outage must
not select a public source fallback or manufacture an empty private register.
